# Existing architecture — inspected baseline

Baseline `9fe94b23eda5251761f188910593ba9e4940469b`; static inspection only. No current data or runtime results are implied.

## Application and flows

`app.py` is a Streamlit single-entry application; `dashboard/common.py::load_data` reads legacy processed/raw CSVs into pandas, caches them, and provides sidebar filters. It is not a native desktop UI. It first calls `ensure_data()` and stops if no legacy CSV exists; this gates even the newer pages. Snapshot UI calls `pipeline.run_scan()` and `pipeline.run_analysis()` synchronously when pressed; it is not a cancellable background monitor.

The eight original pages, exactly as named in `app.py::PAGES`: Overview; File Creation Timeline; Storage Analytics; File Type Analysis; Naming Pattern Analysis; Duplicate Analysis; Folder Structure; Research Findings. Four additive entries are Data Sources (`dashboard/data_sources.py`), Dataset Analysis (`dataset_analysis.py`), Dataset Comparison (`dataset_comparison.py`), Advanced Visualization (`advanced_visualization.py`). Original-page filters and dataset tools are not equivalent to a single native workflow.

Legacy pipeline: `pipeline.py` scans with `FilesystemScanner`, cleans and loads CSVs into pandas, produces temporal/storage/type/naming/duplicate/structure results, writes findings and snapshots and optionally a Markdown research report. The CLI requires an action and drive-root `--yes`, but also exposes `--hash`; the dashboard snapshot path invokes the pipeline directly. `config.py` defaults to `D:\` and creates several directories at import. `run_pipeline.py` is a separate inspect/register CLI for CSV, SQLite or filesystem; it does not provide the desired desktop lifecycle.

## Collection and privacy

`scanner/filesystem_scanner.py` records name, extension, size, timestamps, paths, depth, flags, category, naming features and folder statistics to UTF-8 CSV, plus error rows. It uses `os.scandir`, `stat`, callbacks every 200 completed folders and optional legacy resume. It excludes configured workspace/system directory names; `EXTRA_EXCLUDED_DIRS` is treated as directory names, not an arbitrary robust canonical path exclusion list. The scan root itself bypasses `_is_excluded_dir`. `ScanResult` reports files/folders scanned, size, generic errors and exclusions but not all required discovered, skipped and inaccessible counters.

Per-directory `list(it)` and `subdirs` plus recursive `_walk`, sets of completed folders, and resume's per-path sets make memory grow with directory width, depth and counts. `MAX_DEPTH=64` logs truncation. `scan()` marks a caught fatal walk exception completed. `_record_file` returns 0 for row-write failures, so direct file counts can include a failed record. The code uses `st_ctime` as creation; on POSIX this is metadata change time, not birth time. `st_ctime` semantics on Windows vary with Python version; test current Windows API/runtime and do not infer historical creation when unavailable. Modification and creation dates are not event logs.

`FOLLOW_SYMLINKS=False` and `entry.is_symlink()` guard some cases, but the explicit link check appears in `_record_file`, after directory classification; no explicit Windows reparse-attribute or junction guard is visible on the directory branch. No Windows verification here. `scanner/duplicate_detector.py::find_candidates` labels matching name/extension/size candidates; `verify_candidates` can read file bytes if enabled. `pipeline.py --hash` activates it. `analysis/analysis_runner.py::_sha256` may hash selected registered files or application-owned scan CSVs by default. Such routes cannot be wired unmodified into a strict no-hash desktop scan path.

## Dataset registry and schema

`core/dataset.py` defines source types CSV, SQLite and filesystem, statuses, and a UUID5 derived from resolved, case-folded source path; `source_fingerprint` uses stat size and mtime, not a recursive snapshot fingerprint. `ingestion/dataset_registry.py` maintains SQLite `datasets(dataset_id PRIMARY KEY, name, source_type, source_path, imported_at, metadata_location, validation_status, processing_status, source_fingerprint, row_count, column_count, bytes, notes)` via upsert. Only descriptors are stored, not rows. No snapshot/version table or rename/delete interface is present there.

`FilesystemLoader` writes files/folders/errors CSV into `ProcessingContext.dataset_dir(source-derived-id)` and forces resume off; the reused ID and paths plus write mode can overwrite previous same-source scans. Its metadata `file_size_bytes` sums top-level files only (`load_metadata`), not recursive total. Context guards protected legacy locations but does not generally reject output inside arbitrary scan source. Other writers and temp directories also need unified enforcement. `scanner/database_builder.py` separately deletes/rebuilds the legacy SQLite DB and creates tables from CSV (`files`, `folders`, `scan_errors`, `duplicate_candidates`, `verified_duplicates`, `naming_analysis`, `snapshots` when populated; plus metadata and views). It must not be used as a safe new snapshot store.

`scanner/snapshot_manager.py` persists legacy JSON snapshots and file-level details, then compares path sets and modification timestamps in memory. It is distinct from the registry and has different ownership, scale and preservation constraints.

## Analysis, visualizations, comparison, reports

Legacy `analysis/` includes cleaning, file type, storage, temporal, naming, structure and duplicate summaries; `analysis/analysis_runner.py` and related statistics, frequency, distributions, quality, correlation and outlier modules add streaming/sample/full modes. Not every operation is exact at scale; inspect each result's basis and limits. `analysis/comparison/` supports CSV, SQLite and filesystem matching, metadata comparisons and separate comparison-run outputs; `docs/COMPARISON_GUIDE.md` describes keys, no-key fallback, bounded exports, approximate conditions and limitations. Same-source immutable snapshot registration is not yet guaranteed.

`visualization/chart_registry.py` statically declares 57 chart specs across basic, statistics, multivariate, hierarchical, analysis-run, archaeology and comparison modes. Builders are in `chart_factory.py`, `archaeology_visualizations.py`, `dataset_visualizations.py` and `comparison_visualizations.py`. `filters.py`, `data_adapter.py` and `validation.py` handle filters, bounded previews and checks. `plotly_helpers.figure_to_html` inlines Plotly JS; `visualization/export.py` writes HTML/data/provenance bundles with disclosed row caps. These 57 IDs are not a one-to-one match with the requested 65 research charts. Some generic charts depend on preview/sample frames, not exact full-data aggregates. Static inspection cannot certify every chart or offline rendering.

`analysis/report_generator.py` writes legacy research Markdown and data dictionary. Existing visualization bundles are not the requested complete report pipeline: native PDF, full HTML research reports, Parquet, PNG and SVG need dedicated verification/implementation.

## Tests, dependencies and data

`tests/` contains 22 `test_*.py` files covering synthetic scanner trees, metadata, ingestion/registry, CLI, cleaning, analysis, Streamlit workflows, comparison, chart builders/adapters and exports. `tests/conftest.py` and `tests/fixtures/synthetic.py` describe temp fixtures. The historically dangerous naming test now requests `scanner_config` (`tests/test_analysis_dashboard.py::test_naming_indicator_summary`), but the historical repair of real data is not verifiable here. Tests also deliberately exercise legacy hashing on synthetic files. `requirements.txt` declares only unpinned minimum versions of pandas, numpy, streamlit and plotly; test and desktop dependencies are absent. `README.md`, tracked datasets and Windows launchers are absent. `.gitignore` excludes runtime data/output, logs and databases, with selected report documents allowed; exclusions are not a substitute for a pre-commit privacy review.
