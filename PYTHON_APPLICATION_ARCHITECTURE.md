# Proposed Python desktop architecture — design options for Phase B

This is a proposal, not an implemented schema or acceptance claim. Preserve the existing Streamlit application and research pipeline. Recommend a **separate package inside this repository**, e.g. `desktop_explorer/`, with clearly separated services and tests, not a replacement and not a separate repository yet. It permits reuse and regression testing of mature, UI-independent code while isolating new dependencies, safety rules and release packaging. A separate repository later is reasonable only if independent versioning/distribution or dependency isolation becomes essential; it would otherwise duplicate code and complicate compatibility.

## Boundaries and lifecycle

```text
PySide6 Qt Widgets + Qt WebEngine (local Plotly HTML, JS bundled)
    -> desktop controllers / worker jobs / cancellation event
    -> ScanPolicy + output path guard + dataset service
    -> metadata-only traversal -> batched staging -> immutable snapshot storage
    -> SQL aggregation / sampled chart adapters -> existing compatible pure builders
    -> comparison / evidence-based findings -> reports / exports
    -> SQLite config + registry, DuckDB/Parquet dataset store (proposed)
```

A native folder dialog offers whole drive, root folder and individual folder selections; validate drive roots and offer explicit configuration and confirmation. After consent a worker starts, emits throttled progress and checks a thread-safe cancellation token between entries and batches. UI must never scan, block or open scanned files on its thread. Show partial/error/cancelled states and offer only clearly labelled partial data; no silently completed scans. On completion finalize durable storage before automatic analysis; later jobs also report errors/cancellation. UI presents overview, source, monitor, datasets, statistics/storage/temporal/naming/directory, statistical/visual lab, comparison, insights, exports and settings; enable pages independently of old legacy CSVs.

## Safety policy and output decision

`D:\` with output `D:\Data VMini` conflicts with the literal prohibition on outputs inside the scanned root. **Block implementation of this policy until explicit choice:** strict output outside `D:\` (recommended), or an expressly approved excluded app-owned enclave at `D:\Data VMini` that is a documented exception. Never silently treat path exclusion as meeting the literal no-output-inside-source rule. Under either choice, canonicalize case/volume identities, root/descendant/ancestor relationships, long paths and junction/reparse aliases; fail closed when uncertain. Check both before job start and before every write; route logs, DB, WAL, journals, staging, reports, caches and temp files into the approved app-owned location. Refuse source selection inside app-owned output, and prune all approved output roots before traversal. Do not follow symlinks/junctions/reparse directories, including at the selected root; identify, count and log them. Defend against race/path changes, error out safely if protection cannot be established. Path privacy: dataset filenames and directory metadata are sensitive; local access controls, redacted UI/error logs, no network/telemetry by default, no private metadata in Git.

Scanner opens directories and performs metadata syscalls only: no `open()` on discovered source files, execution, modification, content hashing or archive/image/document parsing. Reuse `scanner/metadata_extractor.py` pure naming/category functions after audit; do not wire `pipeline.py --hash`, duplicate verification or `analysis_runner.verify_source` unmodified. Explicitly selected metadata CSV/Parquet is a different operation: validate schema and read only the selected dataset as data, not files referenced by its rows; clearly explain this exception. Snapshot comparisons operate on stored metadata, never rescan or read referenced source files. Preserve existing legacy routes without claiming they satisfy this desktop policy.

## Storage model (proposed; finalize in B)

* SQLite registry/settings with migrations: `sources(source_id, canonical_root, source_kind)`, `snapshots(snapshot_id UUID, source_id, label, created_at_utc, schema_version, status, validation_status, scan_config_json, software_version, file_count, folder_count, total_bytes, error_count, storage_locator)`, `scan_jobs(job_id, snapshot_id, start/end, counters, status, exclusion_policy, error_summary)`, and optional `comparison_runs` plus explicit output ownership. Use a new ID per scan even for the same root; never upsert historical snapshot data.
* DuckDB/Parquet (or a DuckDB single-writer design selected after prototyping) holds versioned `files(snapshot_id, relative_path, name, extension, size_bytes, created_utc nullable, modified_utc nullable, parent, depth, attrs, naming_features...)`, `directories(snapshot_id, relative_path, parent, depth, direct counts, recursive counts, status...)`, and `scan_errors(snapshot_id, path, stage, error_class, safe_message)`. Store times with timezone and creation-source/availability semantics; retain nulls. Unique per-snapshot paths and useful indexes/partitions as justified by measurements. Directory/file IDs, direct vs recursive size and inaccessible/empty semantics must be specified. Files may change during traversal; snapshot is an observation over a time interval, not atomic filesystem history.
* Incremental bounded batches into uniquely named staging areas; safe commit/transaction status and atomic finalization, recover interrupted jobs without treating partial snapshots as complete. No overwrite; directory cleanup only for application-owned artifacts with containment checks and confirmation. Large scans must use bounded state, disk-backed traversal/aggregates if necessary, no `list(scandir)` or all-record DataFrames.
* CSV/Parquet export from stored metadata streams without truncation. Chart samples, top-N and any approximate quantiles disclose population, method, seed, exclusions and caps; exact totals computed from the whole snapshot. Measure memory, disk use and query time; don't promise an untested million-record target.

## Analysis and presentation

Use SQL for exact counts, sums, distributions, directory and temporal grouping; distinguish direct and recursive totals and never double count ancestor sums. Exact medians/percentiles if feasible; explicitly label any approximations. Use existing pure `analysis/` and `visualization/` functions only when inputs, source restrictions and sample semantics match. Desktop chart adapter gets data lazily, hands Plotly a bounded result and embeds bundled Plotly JS in Qt WebEngine with external navigation/network restricted. Assess offline behavior, licensing and pinned Qt/Plotly versions on Windows. Full 65-item chart request is a coverage goal, not a quota: conditionally offer charts with sufficient valid data, sensible axis units, legends, tooltips, clear empty states, explanation, filtering and export. PCA/t-SNE/clustering require appropriate inputs and limits; timestamp distributions are not proof of work activity.

Research findings carry observation, metric, snapshot ID, chart reference, interpretation and limitation; distinguish hypothesis from observed pattern. Snapshot deltas are valid only for compatible roots, exclusions and time windows; surface mismatches, incomplete scans, moved-file ambiguity and metadata-only duplicate candidates. PDF/HTML reports include methodology, schema, provenance, quality, exact/approximate flags and reproducibility. Use offline export tooling and verify PNG/SVG dependencies and packaging.

## Environment and compatibility

Retain current `requirements.txt` for legacy compatibility unless separately approved; propose a desktop-specific pinned dependency set and development/test lock, with versions and Python/Windows support selected and verified in Phase B. Anticipated dependencies: PySide6 including WebEngine, Plotly, pandas/NumPy where necessary, DuckDB, Parquet support, ReportLab, image exporter and testing tools; SciPy/scikit-learn only if justified. Dependency pinning, licenses, wheel availability and offline installation need a Windows release plan. PySide6 WebEngine and image export support must be validated, not assumed from Linux. No packages installed during Phase A.
